# 06 · 职能分工与设计工作流

> 来源：`research/F-team-workflow.md`（F）为主，结合 B/C/D/E 的技术约束。头部 BG3 mod 团队普遍很小、没有公开过分工表或工时，本文的矩阵与流程是基于案例证据的**草案**，请按实际人手裁剪。

## 1. 每个 mod 需要哪些职能（角色矩阵）F[表 A]

| 角色 | 必需性 | 可否兼任 | 主要交付物 | 介入阶段 |
|---|---|---|---|---|
| **项目所有者 / 维护者** | 必需 | 通常与设计或实现兼任 | Issues/里程碑、Releases、所有权与授权说明（谁能 fork/接手） | 全程 |
| **设计 / 平衡** | 必需 | 可兼任 | 职业设计单（`templates/class-design-doc.md`）、逐级对比表、平衡表 | 概念 → 设计 → 纸面平衡 → 测试迭代 |
| **数据实现（stats / progressions / lists）** | 必需 | 可兼任 | ClassDescriptions、Progressions、ProgressionDescriptions、Lists、Stats 条目、meta.lsx、`.pak` | 技术拆解 → 实现 → 维护 |
| **脚本（SE Lua / Osiris）** | 可选（动态机制、跨 mod API 时必需） | 可兼任，但是独立技能栈 | Lua、`ScriptExtender/Config.json`、CF 集成 | 技术拆解 → 实现 |
| **兼容性 / 框架集成** | 必需 | 通常由实现兼任 | 依赖声明、Conflicts 声明、加载顺序说明、CF 配置 | 技术拆解 → 发布 → 维护 |
| **图标 / 2D 美术** | 必需（可用 CC 素材降级） | 可兼任 | 类图标两版（300×300 + hotbar）、技能图标三尺寸（64/144/380）、mod 缩略图与页面图 | 实现中后期 |
| **VFX / 模型** | 可选 | 独立技能栈，小团队不建议自制 | MEI 文件、EffectBank 引用、VFX 库依赖 | 实现后期 |
| **本地化** | 可选但强烈建议 | 作者提供英文 + 中文；其他语言交社区 | `Localization/<Lang>/*.xml`、文本变更清单（供翻译者增量更新） | 实现末 → 发布 → 维护 |
| **测试 / QA** | 必需 | 作者自测 + Discord 测试者分担 | 测试矩阵结果（`templates/test-matrix.md`）、bug 列表、回归记录 | 内测 → 封闭测试 → 每次补丁后 |
| **社区运营 / 文档** | 必需 | 可兼任 | Nexus/mod.io 页面、README、changelog、FAQ、bug 模板（`templates/bug-report.md`）、Discord 支持 | 发布 → 维护 |

**协作工具事实标准**：GitHub（仓库 / Issue 模板 / Wiki / Releases）+ 官方 BG3 Discord 的 modding 区（#bg3-modding、#bg3-scripting）F[1][2]；未见 Trello/Projects 看板的公开使用证据。

## 2. 分阶段工作流与阶段门（gate）F[表 B]

| # | 阶段 | 交付物 | 进入下一阶段的判据 | 参与职能 |
|---|---|---|---|---|
| 0 | **概念** | 一页概念：职业幻想一句话；最接近的原版"影子基线"职业；与 Patch 8 的 12 个新子职业及 Nexus/mod.io 同类 mod 的差异；**是否允许 SE 依赖**；目标平台（PC / 主机） | 幻想一句话说得清；同类 mod 差异明确；SE 与平台决策已做（决定能否上 mod.io/主机） | 设计、所有者 |
| 1 | **职业设计单（GDD）** | 1–12 级逐级特性表；子职业节点；资源定义；法术列表；每条特性相对影子基线的差异与理由（justify） | 每条特性都有 justify；子职业节点与影子基线一致；无"每回合要跟踪"的 grit 型特性 | 设计 |
| 2 | **纸面平衡** | 按 tier 的 DPR 表、资源节奏表、动作经济表、"横向选项"数量统计 | 数值落在影子基线附近（阈值团队自定）；每级都有变化；复杂度 opt-in | 设计（+1 名评审） |
| 3 | **技术拆解** | 特性 → Progressions / Stats / Lists / Localization / Icons /（Lua）的映射表；每项风险等级；依赖清单；图标与 VFX 需求清单；UUID 对照表 | 每条特性有实现路径与风险等级；"纯数据 vs SE"结论与阶段 0 一致 | 实现、脚本、兼容性 |
| 4 | **实现** | 可运行 `.pak`；先做 1–5 级纵切片再补 6–12；图标先用 CC 素材占位；英文文本 | 新游戏可创建并升到 12 级不崩；无占位文本/丢失图标；多职业不报错；`check_mod.py` 通过 | 实现、脚本、图标 |
| 5 | **内部测试矩阵** | `templates/test-matrix.md` 结果表 | 阻断级 0；每格有记录；已知限制写进 README | 测试、实现 |
| 6 | **封闭测试** | 测试版 + 反馈模板发 Discord 测试者；数值反馈汇总 | 反馈收敛（同一问题不再重复）；平衡表据反馈更新 | 测试、设计、社区 |
| 7 | **发布** | Nexus 页面（+ GitHub 源码）；无 SE 依赖时同步 Toolkit → mod.io；页面含依赖、安装、已知问题、权限（含翻译权限）、Credits、CC-BY 署名；Release 说明 | 页面清单完整；翻译源文件与文本变更清单随包提供；bug 模板已发布；两平台 UUID 相同、Version64 同步 | 社区、所有者 |
| 8 | **维护** | 补丁跟进（72 小时烟测）；Issue 分流；翻译 mod 更新通知；交接/授权预案 | 每次游戏补丁后矩阵烟测完成；所有权与授权关系清晰 | 所有者、实现、社区 |

阶段 0–3 是纸面阶段，便宜、可反复；阶段 4 之后每次返工都要重跑第 5 阶段矩阵，所以 gate 1–3 要严。

## 3. 团队规模 F[表 C]

| 维度 | 最小团队（1–2 人） | 理想团队（4–6 人） |
|---|---|---|
| 组成 | 1 人兼设计 + 实现 + 所有者；第 2 人做测试与图标/文本 | 设计/平衡 1、数据实现 1、脚本 1、图标/VFX 1、QA 1（+ Discord 测试池）、社区/本地化协调 1 |
| 现实对应 | 5e Spells（作者 + 上传者）；Artificer 以 Issues 驱动 | ImpUI 4 位核心作者 + 补丁期贡献者；Community Library "团队 + 独立贡献者" |
| 图标 | Game-Icons.net 等 CC 素材 | 自制风格统一的图集与类图标 |
| VFX | 复用原版或 VFX 库（Shivero、Vlad's Codex） | 少量自定义（AllSpark 四步流程） |
| 本地化 | 英文 + 中文；其余交社区独立翻译 | 内部维护 2–3 种语言并同步更新 |
| 测试 | 自测 + 少量玩家；矩阵覆盖新档/旧档/多职业/重置 | 完整矩阵含联机、荣誉、与主流框架共存；补丁后 72 小时烟测 |
| 兼容性 | 依赖 CL/CF，不自写 API | 可为其他 mod 提供补丁与 API |
| 建议 | 阶段 0–3 做扎实；纯数据优先；一开始写好权限与翻译说明，把社区当"外包团队" | Issue 模板 + Releases 管理；明确所有权与授权 fork 规则，避免维护者离开后 mod 死亡 |

## 4. 设计方法论（5e 自制职业 + BG3 约束）F[2.2][2.3]

### 4.1 共识
- **先职业幻想后机制**（WotC："lean heavily into iconic fantasy stories"，子职业要"擅长兑现其叙事框架"）。
- **与官方职业逐级比较并 justify**（Leuku："特性不存在于真空，而是所有特性叠加的连续体"；"从其他职业借来的每个特性都要证明"）。
- **复杂度 opt-in**（KibblesTasty：区分建卡时的 crunch 与每回合要跟踪的 grit；crunch 可以多，grit 要少）。
- **迭代信号**：强度偏低或"没人选"都是回炉信号（WotC 靠公开 playtest + 问卷）。
- 数值对齐官方，复杂度可以高于官方但必须 opt-in 且不带 grit——本项目采用的立场。

### 4.2 设计检查清单
| 维度 | 检查什么 |
|---|---|
| 幻想与机制一致 | 一句话说清 fantasy；每个核心特性都在兑现它 |
| 伤害基线 (DPR) | 按 tier 与最近的官方职业比较；基线数值需自行从原版数据推算（本次未取得现成表） |
| 资源节奏 | 短休/长休资源数量与回复方式对齐同类官方职业 |
| 特性密度与基础层 | 不重复计算 HP/熟练/额外攻击等"基础层"的价值 |
| 借用特性的正当性 | 逐条 justify |
| 子职业节点 | 与影子基线一致；BG3 里通常 1 级（Cleric/Sorcerer/Warlock 型）或 3 级 |
| 法术槽 | 全施法 / 半施法 / 三分之一施法三选一，不自创曲线 |
| 动作经济 | 附赠动作 / 反应占用与官方同类比较 |
| 复杂度 | crunch 多、grit 少；反应类特性别太多（弹窗负担） |
| 可读性 | 复合特性拆成多个效果；随攻击次数缩放而非固定数值 |

### 4.3 BG3 特有约束
- **12 级上限**：压缩原则——保留官方子职业前三个节点（3/6/10 或 1/6/10），14+ 级特性舍弃或降级合并进 10–11 级，12 级留给最后一次 ASI/专长（ASI 在 4/8/12）；参考 Artificer 的 "12 Levels Option"。若支持 UnlockLevelCurve 则另补 13–20。
- **Patch 8 后的完成度参照**：官方每条新子职业都带动画、VFX、专属召唤物，玩家会以此评价 mod；小团队用复用 VFX + 清晰机制取胜。
- **影子基线量化**：为自创职业选一个原版职业作基线，逐级（1–12）列双方攻击次数、主要资源、法术等级、被动数，在设计单里写差异与理由——原版数据可直接从解包的 Progressions/Stats 读取。
- **UI 承载力**：自定义资源需在 ActionResourceDefinitions 声明才有面板显示（图标仍依赖 ImpUI）；升级界面不能即时显示部分多职业变化；反应以弹窗呈现。
- **多人合作 / 荣誉模式 / 难度**：矩阵必须把新档/旧档/难度模式/多职业作为独立维度；Explorer 难度禁用多职业。
- **发布约束**：依赖 SE → 只能 Nexus、无主机、无 Mac 原生；这个决定在阶段 0 就要做。

## 5. 本地化协作、美术规格、VFX F[2.5]
- **本地化**：作者最低配合——`English/*.xml` 源文件随仓库公开、Nexus 权限里明确允许翻译、每次改文本时在 changelog 列出新增/变更 handle；中文由我们自己出（简体 + 繁体目录），其余交社区独立翻译 mod（Artificer/Mystic/Blood Hunter 均如此）。工具：LocaHelper（3DM 教程）、LarinStudios Localization Helper、BG3LocalizationMerger。Crowdin/Weblate 在 BG3 圈无使用案例。
- **图标规格**：见 02 文档 §5；工具 Photoshop / GIMP / Paint.net + DDS 插件 / NVIDIA Texture Tools；类图标与技能图标在设计单里逐条预留条目，先用 Game-Icons.net（CC BY 3.0）占位。
- **VFX**：官方 Effect Editor "AllSpark" 四部分流程是独立技能栈；社区默认复用原版 VFX 或 VFX 库（Shivero 的 VFX Library、Vlad's Codex）；模型/动画不在职业 mod 常规范围。

## 6. 社区运营与反馈 F[2.6]
- 页面惯例：作者/贡献者署名与接力说明；依赖说明（SE / CF / ImpUI 是否需要）；翻译版与规则变体作为独立条目互链；开源仓库链接；已知限制写正文；标题/标签标补丁版本。
- Bug 报告模板：`templates/bug-report.md`（游戏版本 / 平台 / mod 版本 / 是否 SE / 完整加载顺序 / 新档旧档 / 单机联机 / 难度 / 复现步骤 / 截图或 SE 日志 / Mod Change Tracker 输出）。
- Release 说明至少含：兼容的游戏补丁、是否需要新档、依赖版本、文本变更清单（供翻译者）。
- Discord：官方 BG3 Discord modding 区是招募与求助主渠道；中文触点见 03 文档 §4。
